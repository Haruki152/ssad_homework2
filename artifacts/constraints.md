# 约束清单（由缺陷转化而来）

> 用途：作为 v2 重新生成的**强制性输入**。
> 与契约的区别：契约描述"要做什么"，约束描述"**不许做什么**"，且每条都**可自动验收**。
> 不可验收的约束不算约束，只是建议。

---

## C-01｜禁止在 item 表开业务列
- **来源缺陷**：D-01
- **约束**：`item` 表字段集合必须**严格等于**
  `{item_id, project_id, item_type_id, title, status, owner, custom_attrs}`。
  一切业务属性经 `attribute_definition` 定义后写入 `custom_attrs`。
- **验收方式**：读取实际表结构，与白名单做集合相等比较，多余字段即判失败。
- **对应契约**：D1

## C-02｜属性必须经过定义才能写入
- **来源缺陷**：D-01、D-05
- **约束**：写入 `custom_attrs` 的每个键，必须在该 `item_type` 的 `attribute_definition` 中存在；
  标为 `required` 的属性写入时不得缺失、为 null 或空白文本；所有已提交的值必须满足定义的数据类型；有 `value_domain` 的属性取值必须落在域内。
- **验收方式**：构造"写入未定义属性""缺失必填属性""超出取值域"三个用例，全部必须返回 400。
- **对应契约**：D1

## C-03｜状态流转必须过白名单
- **来源缺陷**：D-02
- **约束**：`item.status` 只能按
  `draft → reviewing → approved → implemented → verified`
  逐级前进，或从任意状态转 `deprecated`。其余跨状态流转一律拒绝并返回 400；保持原状态的更新属于幂等操作，允许。
- **验收方式**：遍历 6×6 全状态组合共 36 例；十条合法边之外，五个非废弃状态的原状态更新按幂等操作接受。API 层共接受 15 组、拒绝 21 组。
- **对应契约**：D2

## C-04｜上游变更必须传播可疑标记
- **来源缺陷**：D-03
- **约束**：`item` 的 `title` 或 `custom_attrs` 被修改时，
  所有 `from_item_id == 该条目` 的 `relationship` 记录必须置 `suspect = true`。
- **验收方式**：建 A→B 关系，改 A 的内容，断言 B 侧关系 `suspect == true`。
- **对应契约**：D3

## C-05｜禁止字符串拼接 SQL
- **来源缺陷**：D-04
- **约束**：所有数据库查询必须使用 ORM 表达式或参数化绑定，**禁止** f-string / `%` / `+` 拼接后交给 `text()` 或 `execute()`。
- **验收方式**：静态扫描，匹配 `execute(text(f"..."))` 一类模式即判失败。
- **对应契约**：新增（安全）

## C-06｜ORM 与 DTO 分层
- **来源缺陷**：D-06
- **约束**：请求模型共用字段通过 ItemFields 继承复用；ORM 列定义与 HTTP 请求模型允许独立定义，因为持久化与输入校验职责不同。
- **验收方式**：人工评审（本条不强制自动验收）。
- **对应契约**：新增（分层）

## 门禁（Quality Gate）

v2 代码必须**全部**满足以下条件才允许进入下一阶段：

| 门禁 | 检查内容 | 通过标准 |
|---|---|---|
| G1 | C-01 schema 一致性 | 表结构字段集合相等 |
| G2 | C-03 状态机 | 36 例全部符合预期 |
| G3 | C-04 可疑传播 | 用例通过 |
| G4 | C-05 静态扫描 | 无拼接 SQL |
| G5 | C-02 属性校验 | 三个反例均返回 400 |
| G6 | 契约接口完整性 | 8 个接口全部存在 |

**任一门禁未通过，不得进入 v2 收尾，必须回退给对应 agent 重新生成。**
